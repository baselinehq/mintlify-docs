Per-card measurements come from the NVIDIA DCGM exporter, which the operator
chart can deploy for you. It is off by default; turn it on with
`dcgm-exporter.enabled` and restrict it to GPU nodes - see
[Configuration](/costgraph/operator/configuration#bundled-exporters).

## What is measured

Three measurements carry the fleet view:

| | |
|---|---|
| Utilisation | how much of the card is busy |
| Framebuffer memory | how much of the card's memory is in use, against its capacity |
| Power | draw against the limit the driver enforces |

Sixteen further signals are collected alongside them: temperature and memory
temperature, SM clock and memory clock, XID errors, correctable and
uncorrectable remapped rows, row-remap failure, total energy, PCIe transmit and
receive bytes, encoder, decoder and memory-copy utilisation, SM active and SM
occupancy.

## Absence is never shown as zero

An idle accelerator and an unmeasurable one look identical once absence is
rendered as 0%. CostGraph reports the state of each measurement instead of
inventing a number, one state per dimension:

| State | What it means |
|---|---|
| `supported` | the card measured it and reports a capacity to express it against |
| `capacity_unknown` | the card measured it but reports no capacity, so there is a number but no percentage |
| `unsupported` | the card is reporting, but cannot report this measurement at all |
| `no_data` | nothing was measured; the card is not reporting |

The practical reading: `no_data` is a collection problem - check the exporter is
running and scheduled on that node. `unsupported` is the hardware, and no
configuration changes it. `capacity_unknown` is usable: the raw measurement
still arrives, in mebibytes for memory and watts for power, so you can read the
value even though a percentage would be a guess. Only `supported` gives a
percentage.

## MIG-partitioned cards

On a card carved into MIG partitions:

- Slices report no overall GPU utilisation. SM active and SM occupancy are the
  utilisation signals a slice has, and both come from the profiling exporter
  below.
- Card-scoped values - power, energy, temperature - are reported once per
  slice, because they describe the whole card. CostGraph collapses them, so a
  seven-slice A100 is not billed seven times its energy.
- Slices carry no namespace, pod, or container label. Per-workload attribution
  on a MIG slice is limited as a result: the partition is visible, the workload
  holding it is not.

## Profiling measurements are opt-in

SM active, SM occupancy and the PCIe byte rates are profiling counters. They
need a second DCGM exporter reading only those counters, which the chart
deploys as its own DaemonSet - `dcgmProfiling.enabled`, off by default.

It is a separate DaemonSet for a reason. The profiling module is not a
per-field opt-out: the exporter watches the whole counter set or exits. Some
accelerators refuse profiling at the driver level, and asking the shared
exporter for a profiling counter on such a card kills that exporter outright,
so the node loses utilisation, memory and power too - and because a DaemonSet
rolls node by node, the refusing pod stalls the rollout for every other GPU in
the fleet.

Which cards serve profiling is discoverable only at runtime, not from a model
list. On a four-node cluster measured this week, L4 and A100-MIG nodes accepted
profiling and a T4 node refused it with:

```
Failed to watch metrics: Error watching fields:
The third-party Profiling module returned an unrecoverable error
```

Expect this on some hardware. What you will see is the profiling pod on that
one node crash-looping while every other GPU node reports normally, and the
profiling measurements for that node reported as unavailable. The base
measurements on the refusing node are unaffected. Narrow the DaemonSet with
`dcgmProfiling.nodeSelector` if you would rather it not schedule there at all.

## Accelerator usage in the product

Container usage can be viewed per accelerator dimension, not only cpu and
memory: overall GPU utilisation, SM active, SM occupancy, framebuffer memory,
and memory-copy utilisation.

For overall GPU utilisation the request and the limit are the whole devices the
container holds. Accelerators are requested as whole integer devices, and
Kubernetes requires the request and the limit to be equal, so there is no
fractional right-sizing: the only move is a different number of whole cards, or
a differently carved card.

## Accelerator cost

Accelerator spend is reported two ways, and they are not the same number:

- **Month to date** covers only the hours elapsed since the start of the current
  UTC month, and never charges a card for hours before it was first seen.
- **Projected month** is what a whole month at the current fleet and rates would
  come to. It is a projection, not spend so far.

Both are estimated from the catalog rate rather than read off an invoice, and
both are withheld rather than shown as zero where any accelerator in the fleet
has no catalog rate, since a partly priced fleet has no known total.
