Releases of the `costgraph-selfhosted` chart, which runs CostGraph in your own infrastructure. Helm release notes are on our [chart repository](https://github.com/BaselineHQ/costgraph-charts); view the [index.yaml](http://charts.costgraph.ai/index.yaml) for the latest published versions.

## SLA
- We will provide changelogs for major and minor releases of the chart
- Customers will be made aware of any breaking changes in any release cycle
- Chart versions are independent of the `costgraph-operator` series, so the numbers do not run continuously


<Note>
    0.2.0 was tagged but never published: the chart repository's release job was failing at the time, and 0.3.0 superseded it. Its only change, moving vmalert to a shared definition, is part of 0.3.0. Nothing was released between 0.1.0 and 0.3.0.
</Note>

<Update label="2026-08-29" description="costgraph-selfhosted v0.5.0">
    ### Breaking Changes

    <Warning>
        A values file written for 0.3.0 still parses against this release and is then ignored, so settings silently fall back to defaults. Work through the migration table in the [values reference](/costgraph/self-hosted/values) before upgrading.
    </Warning>

    - **Every component now takes the same shape.** A component is configured under its own key with `enabled`, `applicationName`, and a `deployment:` block -- or `statefulSet:` for the bundled Postgres and metrics store. The inner keys are identical either way, so sizing or disabling any component is the same operation. The full old-to-new mapping is in the values reference.

    - **Images move to the component.** `global.image` is gone. Each component reads `<component>.deployment.image.{repository,tag,pullPolicy}`. Previously the same setting lived in three different places depending on the component.

    - **`aggregator.vmalert` becomes the top-level `vmalert` component**, with its own `enabled` and `deployment` block.

    - **Removed because nothing read them:** `global.nodeSelector`, `global.tolerations`, `global.affinity`, `global.podAnnotations`. Scheduling is set per component under its workload block.

    - **Supplying your own registry credentials changed.** Setting `global.imagePullSecrets` while a component still names the chart's own registry Secret now fails the render with an explanation, rather than deploying pods that reference a Secret the chart no longer creates. Point each component's `deployment.imagePullSecrets` at your Secret.

    ### Updates
    - `app.kubernetes.io/version` carried a placeholder string rather than the image tag on every object. It now carries the tag
    - The chart's configuration guards had stopped running, so a missing API key or a malformed `appBaseURL` rendered without complaint and failed later at runtime. They run again
    - The migration job requested no CPU or memory because it read a value that had been removed. It now takes the backend's
    - The bundled Redis ran under the `default` service account, and the two bundled datastores mounted a service account token they never used
    - The ingestion API and the aggregator now run with the same container hardening as their siblings: no privilege escalation, a read-only root filesystem, and all capabilities dropped
</Update>

<Note>
    0.4.0 was tagged but never published: 0.5.0 superseded it before a release ran. Nothing was released between 0.3.0 and 0.5.0.
</Note>

<Update label="2026-08-28" description="costgraph-selfhosted v0.3.0">
    ### Breaking Changes

    <Warning>
        Read the first item before upgrading. The Postgres and metrics StatefulSets are renamed, and a renamed StatefulSet does not adopt the volumes of the old one. Upgrading without acting will start both databases against empty storage.
    </Warning>

    - **Every object is renamed and no longer carries the release name.** Objects were `<release>-costgraph-selfhosted...`; they are now `costgraph-selfhosted...`. The chart is installed once per namespace, so the prefix distinguished nothing, and components rendered by the shared application chart cannot reproduce it.

      The two StatefulSets, `costgraph-selfhosted-postgres` and `costgraph-selfhosted-victoria-metrics`, are affected. **Their PersistentVolumeClaims are not deleted**, but the renamed StatefulSets will not claim them and will provision empty volumes instead.

      If you run the bundled Postgres or the bundled metrics store, take a backup first, then either point the release at the existing volumes or restore into the new ones. If you run your own Postgres and metrics store, which is what we recommend for production, nothing here affects your data.

    - **Shared values move under `global`.** A values file using the old paths still parses, and the settings are then ignored, so an install can silently fall back to bundled defaults. Every moved key:

      | Before | After |
      | --- | --- |
      | `postgres.*` | `global.postgres.*` |
      | `redis.url`, `redis.existingSecret`, `redis.bundled.*` | `global.redis.*` |
      | `metricsStore.*` | `global.metricsStore.*` |
      | `controlPlane.*` | `global.controlPlane.*` |
      | `appBaseURL` | `global.appBaseURL` |
      | `corsAllowedOrigins` | `global.corsAllowedOrigins` |
      | `pricingApiKey` | `global.pricingApiKey` |
      | `analytics.*` | `global.analytics.*` |
      | `image.*` | `global.image.*` |
      | `imagePullSecrets` | `global.imagePullSecrets` |
      | `podSecurityContext`, `securityContext` | `global.podSecurityContext`, `global.securityContext` |
      | `nodeSelector`, `tolerations`, `affinity` | `global.nodeSelector`, `global.tolerations`, `global.affinity` |
      | `podAnnotations` | `global.podAnnotations` |

    - **Per-component resources move under `deployment`.** Also silent: the old paths parse and are ignored, and the container then runs with no requests or limits.

      | Before | After |
      | --- | --- |
      | `aggregator.resources` | `aggregator.deployment.resources` |
      | `ingestionApi.resources` | `ingestionApi.deployment.resources` |
      | `redis.bundled.resources` | `redis.deployment.resources` |

    ### Updates
    - The bundled Redis, vmalert, the aggregator and the ingestion API are rendered from shared chart definitions rather than templates unique to this chart, so they no longer drift from the same components in our own deployment
    - vmalert gains a Service per rule set, so `/api/v1/rules` can be reached when a rule is producing no samples. There was no way to reach it before
    - vmalert reads the recording rules from the aggregator image rather than a ConfigMap built from a copy of them, so the rules cannot fall behind the aggregator that consumes them
    - The bundled Redis no longer mounts a service account token
    - Configuration changes roll the affected Deployments again: the pods carry a hash of the values that produced them
</Update>

<Update label="2026-08-27" description="costgraph-selfhosted v0.1.0">
    ### Breaking Changes
    - N/A. First release.

    ### Updates
    - CostGraph running in your own infrastructure: the API, dashboard, ingestion API, aggregator and vmalert, with Postgres, Redis and a VictoriaMetrics store optionally bundled for evaluation
    - Postgres, Redis and the metrics store each take either a URL you provide, a Secret you manage, or a bundled instance. For production we recommend pointing the release at datastores you operate, so cost history outlives a Helm release
    - A preflight check runs before an upgrade and reports a database the release cannot use, rather than failing partway through
</Update>
