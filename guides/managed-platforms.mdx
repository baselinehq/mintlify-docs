---
title: Managed and PaaS platforms
description: "Where the agent can run, and how to install it on managed compute"
---

The agent needs host-level access (host PID, `/proc`, and host networking), so it runs wherever you get a Linux VM. The rule of thumb: if the platform runs your app on instances you can customize, you can run the agent on them.

## Where the agent runs

If your platform gives you VMs or instances, install the agent through the platform's instance-customization mechanism: user data, startup scripts, or platform hooks.

| Platform | How |
| --- | --- |
| Plain VMs (EC2, Compute Engine, Azure VMs, Droplets) | [Install at launch](/costgraph/agent#install) with user data |
| AWS Elastic Beanstalk | [Platform hook](/guides/elastic-beanstalk) |
| AWS ECS on EC2 | [Launch-template user data](/guides/ecs-ec2) |
| GCP managed instance groups | [startup-script](/costgraph/agent#install) on the instance template |
| Azure Virtual Machine Scale Sets | [custom_data](/costgraph/agent#install) or a VM extension |

## Where it can't run

Fully serverless and sandboxed container platforms don't expose the host, so the agent can't run on them: AWS Fargate, GCP Cloud Run, GCP App Engine (standard), Azure App Service and Container Apps, DigitalOcean App Platform, and Heroku.

For Kubernetes (EKS, GKE, AKS), use the [operator](/costgraph/operator/overview) instead of the agent.
